# 문서 분류 엔진 1단계: 연결 계획 (2026-11-21) — 2026-11-21 연결 완료

`doc_registry.py`(문서 지문 목록 + `classify(raw)`)는 만들어 두었고, 아직 앱에 연결하지 않았다.
나중에 연결할 때 아래 순서로 한다. 실제 샘플 5종(요양급여내역, 처방조제정보, 나의건강기록 3종)은 지금 판별과 같은 결과였다.

확신도: 제목 = 높음, 머리글 = 중간, 낱말 = 낮음. 강한 단계가 항상 이긴다.

## 연결할 때 바꿀 곳
1. **공유 처리** (`ingest_screenshot`, 암호 확인 다음): coverage → mhr → checkup 순서 대신 `doc_registry.classify(raw)` 결과로 보낸다.
   - mhr: 지금처럼 `_store_doc("mhr")` + `_process_mhr`
   - medical(높음·중간): `_save_medical_document`
   - coverage, checkup: 보관만 하므로 확신도와 관계없이 지금처럼 자동 보관
   - 그 밖의 낮은 확신도: 문서함(locked, 열린 상태)에 `suggested` 를 달아 보관
   - 결과 없음: 지금처럼 Gemini 의료비 읽기 (4번 참고)
2. **`_guess_kind`**: `doc_registry.classify(raw)["box"]` 로 바꾼다. 공유 직후와 암호 해제 후가 같은 순서가 된다.
3. **화면 분류(screen_router)**: 실패(키 없음, 오류, 잘못된 JSON)를 "error" 로 돌려주고 저장하지 않는다
   ("❌ 화면 종류를 판단하지 못했습니다. 잠시 후 다시 시도해 주세요."). "other" 는 지금처럼 맛집 읽기를 시도한다
   (실제 음식 게시물이 other 로 나오는 경우가 있고, 가게가 없으면 이미 '찾지 못함'으로 끝난다).
4. **모르는 PDF 보관**: Gemini 의료비 읽기가 아무것도 못 찾으면 버리지 않고 문서함에 열린 상태로 보관한다.
   ("📥 의료비 내용을 찾지 못해 문서함에 보관했습니다. 종류를 골라 주세요.")
5. **같은 암호로 모두 열기 / 추정대로 모두 저장** (요양급여내역 연도별 10개 파일 대비):
   `doc_open`·`doc_classify` 본문을 `_open_one`·`_classify_one` 으로 빼고,
   `POST /api/docs/open-all {password}` → {opened, failed}, `POST /api/docs/classify-all` → {saved, failed, messages}
   (의료비 처리는 하루 한도에서 멈춤). docs.html 암호 문서함에 버튼 두 개(해당 문서 2개 이상일 때).

## 남은 확인
- 건강검진·보장분석 제목 규칙은 실물로 확인하지 못했다(보장분석 샘플 암호 다름). 지금은 낱말 규칙이 받쳐 준다.
- `_REPORT_TERMS`, `mhr._split` 을 다른 모듈에서 가져다 쓴다. 연결할 때 공개 이름으로 바꾼다.
- 2단계(Gemini 쪽 단위 판정, 기존과 나란히 비교) → 3단계(예시 검색 + 사용자 수정이 샘플로 쌓임) → 4단계(손 규칙 정리)는
  연구 조사 결과(2026-11-21 대화)의 단계별 도입안을 따른다.
